# 实现文件级并行编译（每个文件生成独立C文件）

## 目标

实现文件级并行编译，每个 uya 文件独立编译生成一个 C 文件，然后链接所有 C 文件。支持三种编译模式、模块级头文件、增量编译和线程并行。

## 三种编译模式

| 模式 | 输入 | 输出 | 适用场景 |
|------|------|------|----------|
| **单文件** | `app.uya` | `app.c` | 脚本、小工具 |
| **多文件** | `src/*.uya` | `*.c + *.h` | 开发者应用 |
| **增量编译** | 修改的文件 | 只重编修改的 `.c` | 大型项目 |

## 模块级头文件策略

### 源文件示例

```uya
// src/parser.uya
use std.io;
use lexer;

export struct Parser { ... }       # → parser.h
export fn parse() { ... }          # → parser.h (声明)
fn internal_helper() { ... }       # → 仅 parser.c (static)
```

### 生成的头文件

```c
// parser.h
#ifndef PARSER_H
#define PARSER_H

#include "uya_types.h"
#include "lexer.h"  // 依赖

// export 结构体定义
struct Parser { ... };

// export 函数声明
extern struct ASTNode* parse();

#endif
```

### 生成的源文件

```c
// parser.c
#include "parser.h"

// 非 export 函数定义 (static)
static void internal_helper() {}

// export 函数定义
struct ASTNode* parse() { ... }
```

## static 函数处理

### 当前逻辑（c99/function.uya）

```uya
var is_static: i32 = 0;
if is_main == 0 && is_extern == 0 && is_export == 0 && has_extern_decl_same_name == 0 && extern_lib_name == null {
    is_static = 1;
}
```

| 函数类型 | static | 可见性 |
|----------|--------|--------|
| `export fn` | ❌ | 全局可见（需 extern 声明） |
| `fn` | ✅ | 文件内可见 |
| `extern fn` | ❌ | 外部链接 |

### 多文件模式处理

1. **公共头文件（uya_types.h）**：所有结构体、枚举定义
2. **模块头文件（xxx.h）**：该模块的 export 函数声明
3. **源文件（xxx.c）**：
   - 包含对应的模块头文件
   - static 函数仅在当前 .c 文件可见
   - export 函数不使用 static

## 增量编译流程

```
┌───────────────────────────────────────────────────────────────┐
│                      增量编译流程                              │
├───────────────────────────────────────────────────────────────┤
│                                                               │
│  1. 检查修改                                                   │
│     ┌─────────────────────────────────────────┐               │
│     │ 读取 timestamps.json                    │               │
│     │ 对比每个 .uya 文件的 mtime              │               │
│     │ 找出修改的文件: [parser.uya, utils.uya] │               │
│     └─────────────────────────────────────────┘               │
│                           │                                   │
│                           v                                   │
│  2. 依赖传播                                                   │
│     ┌─────────────────────────────────────────┐               │
│     │ 读取 deps.json                          │               │
│     │ 找出依赖修改文件的其他文件:              │               │
│     │   parser.uya 被 codegen.uya 依赖        │               │
│     │   → 需要重编: codegen.uya               │               │
│     └─────────────────────────────────────────┘               │
│                           │                                   │
│                           v                                   │
│  3. 类型检查                                                   │
│     ┌─────────────────────────────────────────┐               │
│     │ 如果 types.cache 有效，跳过类型收集     │               │
│     │ 否则重新收集全局类型                    │               │
│     └─────────────────────────────────────────┘               │
│                           │                                   │
│                           v                                   │
│  4. 并行生成                                                   │
│     ┌─────────────────────────────────────────┐               │
│     │ 只重新生成修改的 .c 文件                │               │
│     │ 使用线程池并行生成                      │               │
│     └─────────────────────────────────────────┘               │
│                           │                                   │
│                           v                                   │
│  5. GCC 并行编译                                               │
│     ┌─────────────────────────────────────────┐               │
│     │ gcc -j4 -c parser.c codegen.c          │               │
│     │ gcc *.o -o app                          │               │
│     └─────────────────────────────────────────┘               │
│                                                               │
└───────────────────────────────────────────────────────────────┘
```

## 编译缓存格式

### deps.json - 依赖图

```json
{
  "modules": {
    "parser": {
      "file": "src/parser.uya",
      "imports": ["std.io", "lexer"],
      "exports": ["Parser", "parse", "Token"]
    },
    "codegen": {
      "file": "src/codegen.uya", 
      "imports": ["parser", "std.io"],
      "exports": ["CodeGenerator", "generate"]
    }
  },
  "dependents": {
    "parser": ["codegen", "main"],
    "lexer": ["parser"]
  }
}
```

### timestamps.json - 文件修改时间

```json
{
  "src/parser.uya": 1739876543,
  "src/codegen.uya": 1739876500,
  "src/main.uya": 1739876400
}
```

## 技术挑战

### 1. 类型检查的跨文件访问

- 当前类型检查器需要访问所有声明
- 新方案需要访问全局类型表
- 解决方案：Phase 1 收集全局类型，Phase 2 只读访问

### 2. 头文件生成

- 结构体、枚举需要在所有文件中可见
- export 函数需要 extern 声明
- 解决方案：公共头文件 + 模块级头文件

### 3. 循环依赖检测

- 在依赖分析阶段检测循环依赖
- 使用拓扑排序确定编译顺序

### 4. 线程安全

- 类型表只读访问（线程安全）
- 每个线程独立的输出缓冲区
- Arena 分配器需要线程本地存储或加锁

## 注意事项

1. **向后兼容**：保持与现有单文件输出模式的兼容性
2. **错误处理**：线程中的错误需要正确传递到主线程
3. **内存管理**：每个文件使用独立的 Arena
4. **性能优化**：小文件可能不如串行快，需要根据文件数量动态选择
5. **链接器依赖**：需要系统有 gcc 或 clang 链接器
